## Splitting queues between instances

Requests come in two queues: `all` for analysis, search and indexing, and `train` for model training. One instance
consumes both by default. To give training its own resources, run two instances and give each one a queue:

| Instance      | Settings                   |
|---------------|----------------------------|
| Analysis only | `ANALYZER_TRAIN_WORKERS=0` |
| Training only | `ANALYZER_WORKERS=0`       |

Don't set `DISABLE_TRAIN=true` on either instance. It means "no training at all": the instance consumes the `train`
queue and discards every message from it, whatever `ANALYZER_TRAIN_WORKERS` is. On the analysis instance it would
take training requests from the training instance and drop them.

An instance with both `ANALYZER_WORKERS=0` and `ANALYZER_TRAIN_WORKERS=0` has nothing to consume, and it exits at
startup with an error. Requests to train models need no extra setup:
the analysis instance publishes them to the `analyzer` exchange and RabbitMQ delivers them to the `train` queue,
whichever instance consumes it.

Limitations:

* **One instance per queue.** Requests of one project run one at a time, in publish order, only within one instance.
  Two instances which consume the same queue process requests of one project in parallel and out of order: for
  example, a `delete` can overtake the `index` it follows, and the index becomes inconsistent. Don't run several
  instances with the same queue enabled.
* **Shared model storage.** The training instance saves models and the analysis instance loads them, so both must use
  the same storage. With `DATASTORE_TYPE=minio` or `s3` nothing else is needed. With `filesystem` mount the same volume
  at `FILESYSTEM_DEFAULT_PATH` in both containers, otherwise the analysis instance never sees the trained models.
* **Each queue needs a consumer.** A queue with 0 workers on every instance is consumed by nobody, and it grows
  forever. The `analyzer` exchange is a fanout one, so every message reaches both queues, and this applies even if no
  training is ever requested.
* **Start both instances at least once before use.** An instance declares only the queues it consumes. A request
  published to the `analyzer` exchange before its queue was declared is lost, because the exchange has nowhere to
  route it. Queues are durable, so after the first start messages wait in the queue while its instance is down.

## Instructions for analyzer setup without Docker

Install python with the version 3.7.4. (it is the version on which the service was developed, but it should work on the versions starting from 3.6).

Perform next steps inside source directory of the analyzer.

### For Linux:

#### Analyzer

1. Create a virtual environment with any name (in the example **/venv**)
```bash
  python -m venv /analyzer
```
2. Install python libraries
```bash
  /analyzer/bin/pip install --no-cache-dir -r requirements.txt
```
3. Activate the virtual environment
```bash
  /analyzer/bin/activate
```
4. Install stopwords, wordnet and omw-1.4 package from the nltk library
```bash
  /analyzer/bin/python3 -m nltk.downloader -d /usr/share/nltk_data stopwords wordnet omw-1.4
```
5. Start the analyzer
```bash
  /analyzer/bin/python3 app/main.py
```
